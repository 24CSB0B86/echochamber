1. PROJECT OVERVIEW
================================================================================

EchoChamber is a full-stack, production-hardened, real-time chat application
with a unique distinguishing feature: the SAME message is experienced
differently by every recipient based on their personality profile.

The project was built as a learning exercise that deliberately identifies and
fixes 11 performance bottlenecks that would kill a naive implementation at
scale. Every architectural decision is documented with a rationale and an
interview-ready explanation.

Total cost to run: $0.00 (all services used have free tiers)
Build time: approximately 2 weeks
Prompts used to build it: 4 (architectural phases)

================================================================================
2. WHAT ECHOCHAMBER DOES (Core Concept)
================================================================================

1. USER SIGNS UP: Registers with email + password via Supabase Auth.

2. PERSONALITY ONBOARDING: Answers 5 rapid-fire questions that generate:
   - A unique HEX color (deterministic, from answer sum % 12)
   - An avatar shape (circle/triangle/square/hexagon/star)
   - A typeKey (e.g. "analytical:verbal") used for message reframing grouping
   - Personality traits: setting, time, response, social, medium

3. ENTERS A CHAT ROOM: Connects via WebSocket (Socket.io).

4. SENDS A MESSAGE: The raw text is broadcast via Redis Pub/Sub to all server
   instances. Then Groq's Llama 3.1 API reframes the message tone for EACH
   unique personality type present in the room — in parallel, and cached.

5. RECIPIENTS SEE THEIR VERSION: Each user sees the message reframed to match
   their personality type. The sender always sees their own original message.
   Reframing is invisible to users by default (they can toggle to see original).

6. ROOM HAS EMOTIONAL WEATHER: Every message triggers a sentiment analysis
   (using the 'sentiment' npm package — no API call, ~1ms). The rolling average
   of sentiment scores determines the room's weather state (calm/warm/heated/
   tense/stormy), displayed as a Canvas animation in the background.
   This is computed AFTER message delivery so it never delays the message.

7. DATABASE SCHEMA (Supabase / PostgreSQL)
================================================================================

FILE: backend/db/schema.sql

--- TABLE: profiles ---
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid()
  user_id          uuid REFERENCES auth.users(id) ON DELETE CASCADE
  color            varchar(7)      -- hex color e.g. '#7c6ff7'
  avatar           varchar(20)     -- 'circle'|'triangle'|'square'|'hexagon'|'star'
  personality_json jsonb           -- { setting, time, response, social, medium, typeKey }
  display_name     varchar(50)
  created_at       timestamptz DEFAULT now()

  Index: profiles_user_id_idx (unique) on user_id

  RLS Policies:
    - SELECT: public (anyone can read profiles)
    - ALL (INSERT/UPDATE/DELETE): auth.uid() = user_id (own row only)

--- TABLE: rooms ---
  id            uuid PRIMARY KEY DEFAULT gen_random_uuid()
  name          varchar(80) UNIQUE NOT NULL
  description   varchar(200)
  created_by    uuid REFERENCES auth.users(id) ON DELETE SET NULL
  synced_count  integer DEFAULT 0   -- synced from Redis INCR every 60s
  created_at    timestamptz DEFAULT now()

  NOTE: NO real-time message_count column (bottleneck fix #5).
        Message counts live in Redis key "msgcount:{roomId}" and are
        synced to synced_count every 60 seconds by syncRoomCounts.js.

  RLS Policies:
    - SELECT: public
    - INSERT: auth.uid() IS NOT NULL (any authenticated user)
    - UPDATE: auth.uid() = created_by (room creator only)

--- TABLE: messages ---
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid()
  room_id     uuid REFERENCES rooms(id) ON DELETE CASCADE
  sender_id   uuid REFERENCES auth.users(id) ON DELETE SET NULL
  content     text NOT NULL        -- raw content only, reframed is never stored
  sent_at     timestamptz DEFAULT now()

  NOTE: The app inserts messages with a client-generated UUID via uuid() in
        roomHandler.js. The schema allows this (no ALWAYS GENERATED constraint).

  Index: idx_messages_room_sent on (room_id, sent_at DESC)
         -- optimizes "give me last 50 messages in room X" query

  RLS Policies:
    - SELECT: public (chat is public within rooms)
    - INSERT: auth.uid() = sender_id (can only send as yourself)

8. REDIS KEY SCHEMA
================================================================================

Key Pattern                  | Type   | Content                        | TTL
-----------------------------|--------|--------------------------------|-------
auth:{token}                 | String | "{userId}|{email}"             | 300s (5min)
profile:{userId}             | Hash   | All personality fields         | None
history:{roomId}             | List   | Last 50 JSON message strings   | None
room:{roomId}:members        | Set    | Set of userId strings          | None
presence:{roomId}:{userId}   | String | "1"                            | 30s
ratelimit:{userId}           | String | Message count integer          | 60s (window)
msgcount:{roomId}            | String | Message count integer          | None
roomcount:{roomId}           | String | Member count integer           | None
weather:{roomId}             | List   | Last 20 sentiment score strings| None
weatherts:{roomId}           | List   | Last 20 timestamp strings      | None
roomweather:{roomId}         | Hash   | { state, avgScore, velocity,  | 120s
                             |        |   volatility }                 |
reframe:{hash16}:{typeKey}   | String | Groq reframed text             | 3600s (1hr)

Pub/Sub Channels:
  room:{roomId}    -- chat messages (subscribed by pubsub.js with pattern "room:*")
  weather:{roomId} -- weather updates (subscribed with pattern "weather:*")

Notes on design decisions:
  - "auth:{token}": key is the full JWT string. ioredis handles long keys.
  - "reframe:{hash}:{typeKey}": hash is sha256(rawContent).slice(0,16) — 16
    chars is 64-bit which is collision-resistant for a chat app. Keeps keys small.
    Key example: "reframe:a3f1b2c4d5e6f7a8:analytical:verbal"
  - "room:{roomId}:members": Redis Set (not KEYS pattern) for O(1) add/remove
    and O(members) list — crucial for avoiding the KEYS anti-pattern.
  - presence TTL 30s: client sends heartbeat every 20s. If client dies without
    leave_room, key auto-expires within 30s.
  - WEATHER_WINDOW = 20 (last 20 scores/timestamps kept)
  - WEATHER_TTL = 120s (roomweather hash expires if room goes quiet)

--- 9.1 ENTRY POINT: src/index.js ---

Purpose: Bootstraps the entire backend server.

What it does:
  1. Imports dotenv/config (ES module import, not require)
  2. Creates Express app and HTTP server
  3. Configures CORS: reads FRONTEND_URL from env (comma-separated for multiple
     origins), always allows localhost:5173 and 5174 for local development
  4. Configures express.json() with 10kb limit (rejects oversized payloads)
  5. Registers routes:
     GET  /health             → health check endpoint (for Render)
     /api/onboarding          → onboardingRouter
     /api/profile             → profileRouter
     /api/rooms               → roomsRouter
  6. 404 and global error handlers
  7. Creates http.Server (needed to share with Socket.io)
  8. Calls initSocket(server) to set up WebSocket layer
  9. Listens on PORT (default 3001)
 10. Calls startSyncJob() to begin write-behind sync job
 11. Registers SIGTERM/SIGINT handlers for graceful shutdown:
     - clearInterval(syncJobId)
     - io.close()
     - server.close()

Key code details:
  const ALLOWED_ORIGINS = [
    'http://localhost:5173',
    'http://localhost:5174',
    ...(process.env.FRONTEND_URL
      ? process.env.FRONTEND_URL.split(',').map(u => u.trim())
      : []),
  ];

  Reason: FRONTEND_URL can be a comma-separated list of allowed origins,
  supporting both production Vercel URL and local dev simultaneously.

  CORS is configured with credentials: true (required for cookies/auth).
  Requests with no origin (curl, Postman) are allowed through.

  NOTE: startSyncJob() runs AFTER server.listen() — this is by design so the
  server starts serving immediately and the background job is a side effect.

--- 9.2 AUTHENTICATION MODULE: src/auth/supabase.js ---

Purpose: Supabase client factory + auth helper functions.

Exports three clients:
  1. supabase (default export): anon key singleton. Used for auth ops.
     RLS applies. Never used for DB writes from server.

  2. createUserClient(token): Per-request factory. Creates a Supabase client
     that sends the user's JWT on every request via Authorization header.
     Supabase sees auth.uid() = real user, so RLS passes correctly.
     NOT a singleton — each request gets its own client so tokens never bleed.
     Configuration:
       global: { headers: { Authorization: `Bearer ${token}` } }
       auth: { persistSession: false }
     Usage: const userClient = createUserClient(req.token)

  3. supabaseAdmin: service role key client. Bypasses RLS entirely.
     ONLY for background jobs (syncRoomCounts.js).
     Falls back to anon client with console.warn if SERVICE_ROLE_KEY not set.
     NEVER expose this key to the frontend.

Auth helper functions (thin wrappers — nothing imports supabase-js directly):
  - signUp(email, password)   → supabase.auth.signUp({ email, password })
  - signIn(email, password)   → supabase.auth.signInWithPassword(...)
  - signOut()                 → supabase.auth.signOut()
  - getUser(token)            → supabase.auth.getUser(token) ← NETWORK CALL

Why getUser is expensive:
  It's an HTTP call to Supabase's auth server (~50-100ms per call).
  This is what the Redis token cache (auth middleware) is designed to avoid
  calling more than once per 5-minute window.

Startup validation:
  if (!supabaseUrl || !supabaseAnonKey): throws Error with clear message.
  Fails fast on startup rather than crashing mid-request.

--- 9.3 AUTH MIDDLEWARE: src/middleware/auth.js ---

Purpose: Validates Bearer JWT on every protected REST request.
         BOTTLENECK FIX #4: Redis token cache to avoid repeated Supabase calls.

Flow:
  1. Read Authorization: Bearer {token} header → return 401 if missing
     (checks for "Bearer " prefix)
  2. Check Redis: GET "auth:{token}"
     - HIT: parse "{userId}|{email}" via split('|') → set req.user + req.token → next()
     - MISS: call supabase.getUser(token) [expensive ~50-100ms network call]
             → if invalid: return 401
             → if valid: SET "auth:{token}" "{userId}|{email}" EX 300
             → set req.user + req.token → next()
  3. Error: return 500

Configuration:
  TOKEN_CACHE_TTL = 300 (5 minutes) — same value in socket/index.js

Why pipe-separated "{id}|{email}" instead of JSON?
  Avoids JSON.parse overhead on every cache hit. Simple split('|') is faster.

Why this is safe:
  JWTs are immutable. If a user logs out, Supabase invalidates the session
  server-side. Worst case: a logged-out user's token stays cached for 5 minutes.
  Acceptable for a chat app. For banking: add a Redis blocklist on logout.

req.token is attached so route handlers can create user-scoped Supabase clients
(createUserClient(req.token)) that pass RLS policies correctly.

--- 9.4 ONBOARDING ROUTE: src/routes/onboarding.js ---

Purpose: Computes personality profile from quiz answers and stores it in
         both Redis (live source of truth) and Supabase (durable backup).

Endpoint: POST /api/onboarding (protected via authMiddleware)

Request body: { answers: [1,2,1,3,2], displayName: "Alice" }
  - answers: array of exactly 5 integers, each 1-3
  - Validation: !Array.isArray || length !== 5 → 400
  - Per-answer validation: !Number.isInteger || a < 1 || a > 3 → 400

Personality mappings (deterministic from answer index):
  Q1 (answers[0]): 1→'nature', 2→'ocean', 3→'urban'            → trait: setting
  Q2 (answers[1]): 1→'night',  2→'day',   3→'evening'           → trait: time
  Q3 (answers[2]): 1→'analytical', 2→'emotional', 3→'avoidant'  → trait: response
  Q4 (answers[3]): 1→'introvert', 2→'ambivert', 3→'extrovert'   → trait: social
  Q5 (answers[4]): 1→'verbal', 2→'visual', 3→'auditory'         → trait: medium

Derived values:
  typeKey:   `${response}:${medium}` e.g. "analytical:verbal"
             9 possible combinations (3×3). Grouping key for Groq reframing.
  color:     COLOR_PALETTE[answerSum % 12]  (sum of all 5 answers, range 5-15)
  avatar:    AVATAR_SHAPES[(answers[2] - 1) % 5]  (based on Q3 answer)
  displayName: displayName?.trim() || `User${userId.slice(0,6)}`

COLOR_PALETTE (12 colors, deterministic):
  '#7c6ff7' violet, '#4ecdc4' teal, '#f7c948' amber, '#ff6b6b' coral,
  '#a8e6cf' mint, '#c9b1ff' lavender, '#ff9a3c' orange, '#00b4d8' sky blue,
  '#f72585' pink, '#3a86ff' bright blue, '#80ffdb' seafoam, '#ffbe0b' yellow

AVATAR_SHAPES: ['circle', 'triangle', 'square', 'hexagon', 'star']
  Note: only 3 shapes are directly accessible (answers 1,2,3 → indices 0,1,2)
  Hexagon/star would require answers > 3 (currently not possible)

Storage:
  1. Redis HSET "profile:{userId}" {...profile}  (no TTL — permanent)
     Uses HSET which allows individual field reads (HGET "profile:X" "typeKey")
  2. Supabase upsert into profiles table using createUserClient(req.token)
     (uses onConflict: 'user_id' so re-taking onboarding updates the row)
     Supabase data shape:
       { user_id, color, avatar, display_name, personality_json: {...} }

Response: 201 { profile: { userId, displayName, setting, time, response, social,
                              medium, typeKey, color, avatar } }

Error handling: If Supabase write fails, the request still succeeds (Redis is
the live source of truth). The failure is logged but not propagated.

--- 9.7 SOCKET.IO SETUP: src/socket/index.js ---

Purpose: Creates Socket.io server, attaches auth middleware, starts pub/sub.

initSocket(httpServer):
  1. Creates io = new Server(httpServer, { cors: { origin: FRONTEND_URL } })
     NOTE: Socket.io CORS uses the raw string from FRONTEND_URL, NOT the
     comma-separated multi-origin array that Express CORS uses. Single origin only.
  2. Attaches auth middleware (runs ONCE per connection attempt):
     a. Read token from socket.handshake.auth?.token → reject AUTH_MISSING if missing
     b. Check Redis "auth:{token}" cache (same cache as HTTP middleware)

  3. On 'connection': calls registerRoomHandlers(io, socket)

  Storing the profile on the socket object means ZERO Redis calls during message

--- 9.8 ROOM HANDLER: src/socket/roomHandler.js ---

Purpose: All Socket.io room event handlers. The core real-time logic.

Imports:
  - uuid from 'uuid' (for message id generation)
  - redis from '../lib/redis.js'
  - createUserClient from '../auth/supabase.js'
  - reframeAndDeliver from './reframeHandler.js'
  - analyzeMessage, updateRoomWeather from '../services/sentiment.js'
  - INSTANCE_ID from '../lib/instanceId.js'

Rate limit constants:
  RATE_LIMIT_MAX    = 30  (messages)
  RATE_LIMIT_WINDOW = 60  (seconds)

Redis key schema managed here:
  "room:{roomId}:members"      — Set of active userIds
  "presence:{roomId}:{userId}" — TTL key "1" EX 30
  "history:{roomId}"           — List of last 50 messages
  "ratelimit:{userId}"         — Counter with EXPIRE
  "msgcount:{roomId}"          — Message count
  "roomcount:{roomId}"         — Room member count

Event handlers:

  'join_room' ({ roomId }):
    1. socket.join(roomId)  [Socket.io room]
    2. SADD "room:{roomId}:members" userId  [O(1) — BOTTLENECK FIX #3]
    3. SET "presence:{roomId}:{userId}" "1" EX 30
    4. SMEMBERS "room:{roomId}:members" → get all member IDs
    5. Pipeline HGETALL for each member profile [ONE round trip]
       Filters out entries where profile?.userId is falsy
    6. LRANGE "history:{roomId}" 0 49 → JSON.parse + reverse (oldest first)
    7. HGETALL "roomweather:{roomId}" → current weather if exists
    8. Emit to joining socket:
       - 'room_history' { roomId, messages: history }
       - 'online_users' { roomId, users: onlineUsers }
       - 'weather_update' parsed HASH if weather.state exists
         (avgScore → parseFloat, velocity → parseInt, volatility → parseFloat)
    9. socket.to(roomId).emit('user_joined', { roomId, userId, profile })
   10. INCR "roomcount:{roomId}"
   11. console.log count of online users

  'send_message' ({ roomId, content }):
    STEP 1: Rate limiting (token bucket)
      const key = "ratelimit:{userId}"
      const count = await redis.incr(key)
      if count === 1: redis.expire(key, RATE_LIMIT_WINDOW)   [starts 60s window]
      if count > RATE_LIMIT_MAX: emit 'rate_limited' → return
      NOTE: INCR+EXPIRE is not atomic. Use Lua script in production:
        redis.eval("local c=redis.call('INCR',KEYS[1])
                    if c==1 then redis.call('EXPIRE',KEYS[1],60) end
                    return c", 1, key)

    STEP 2: Validate + build message object
      trimmed = content.trim().slice(0, 500)
      if (!trimmed) return
      { id: uuid(), roomId, senderId, rawContent: trimmed, content: trimmed,
        sentAt: new Date().toISOString(), senderProfile: socket.profile,
        instanceId: INSTANCE_ID }
      senderProfile: socket.profile  ← from socket object, ZERO Redis calls

    STEP 3: Pipeline — 4 Redis commands in ONE round trip
      pipeline.lpush("history:{roomId}", messageJson)
      pipeline.ltrim("history:{roomId}", 0, 49)
      pipeline.incr("msgcount:{roomId}")
      pipeline.publish("room:{roomId}", messageJson)
      await pipeline.exec()
      [BOTTLENECK FIX #2: was 4 separate calls at ~20ms each = ~80ms]

    STEP 4: Supabase insert — fire and forget (no await)
      const userClient = createUserClient(socket.token)
      userClient.from('messages').insert({
        id, room_id: roomId, sender_id: socket.userId,
        content: trimmed, sent_at: sentAt
      }).then(...)
      [Redis is live source of truth; Supabase is durable backup]

    STEP 5: reframeAndDeliver(io, message) — await
      [Delivers reframed content to each recipient by personality type]

    STEP 6: setImmediate(() => { analyzeMessage; updateRoomWeather })
      [BOTTLENECK FIX #6: weather runs AFTER message delivery — never blocks]
      Note: setImmediate vs setTimeout(fn, 0) — setImmediate runs in the "check"
      phase (after I/O) and is more semantically explicit. Both work here.

  'heartbeat' ({ roomId }):
    SET "presence:{roomId}:{userId}" "1" EX 30
    [Client sends every 20s — keeps presence alive]

  'leave_room' ({ roomId }):
    Delegates to _leaveRoom(io, socket, roomId)

  'disconnect':
    For every room in [...socket.rooms].filter(r => r !== socket.id):
      calls _leaveRoom(io, socket, roomId)
    (socket.rooms includes the socket's own ID as a special room — filtered out)

Internal helper _leaveRoom(io, socket, roomId):
  socket.leave(roomId)
  SREM "room:{roomId}:members" socket.userId
  DEL "presence:{roomId}:{socket.userId}"
  io.to(roomId).emit('user_left', { roomId, userId: socket.userId })
  console.log

--- 9.9 REDIS PUB/SUB: src/socket/pubsub.js ---

Purpose: Horizontal scaling via Redis Pub/Sub. Routes messages from other server
         instances to the sockets connected to THIS instance.

Why a separate Redis client?
  A subscribed Redis client can ONLY send SUBSCRIBE/UNSUBSCRIBE/PING.
  It cannot run HGETALL, LPUSH, etc.
  Creating a dedicated subscriber keeps the main redis client free.
  The subscriber uses maxRetriesPerRequest: null (retry forever — critical for
  long-running subscriber connections).

startPubSub(io):
  1. Creates new Redis(REDIS_URL) subscriber client with TLS if rediss://
  2. psubscribe('room:*', 'weather:*')  [two patterns in one call]
  3. On 'pmessage' (pattern, channel, payload):

     IF pattern === 'room:*':
       Parse roomId from channel ("room:".length slice)
       Parse message JSON

       CRITICAL: instanceId check
         if message.instanceId === INSTANCE_ID:
           SKIP — reframeAndDeliver already handled this on THIS instance
         else:
           reframeAndDeliver(io, message).catch(...)
           [cross-instance message — OUR clients didn't get it yet]

     IF pattern === 'weather:*':
       Parse roomId + weather JSON
       io.to(roomId).emit('weather_update', weather)
       [No instanceId check needed — weather is idempotent]

Returns the subscriber client (currently unused by caller but good practice).

The instanceId problem (why it exists):
  roomHandler.js calls pipeline.publish("room:{roomId}", message) AND THEN
  calls reframeAndDeliver(io, message). The pub/sub subscriber runs in the SAME
  process and receives the publish event during the first await inside
  reframeAndDeliver. Without the instanceId check:
    - pubsub emits raw message to room (arrives first)
    - frontend deduplicates by message ID → raw version wins
    - reframed version arrives later but gets dropped (ID already seen)
    - Result: ALL users see the unframed raw message. Reframing silently fails.

  With instanceId check: same-instance messages are skipped by pubsub.
  reframeAndDeliver handles delivery with the correct personality-specific content.

--- 9.10 REFRAME HANDLER: src/socket/reframeHandler.js ---

Purpose: The core bottleneck fix #1. Reduces N Groq calls to at most 9,
         cached in Redis, delivered in parallel.

reframeAndDeliver(io, message):

  STEP 1: Get all socket IDs in the room
    const roomSockets = io.sockets.adapter.rooms.get(message.roomId)
    Return early if null or size === 0

  STEP 2: Group sockets by typeKey — ZERO Redis calls
    for socketId in roomSockets:
      socket = io.sockets.sockets.get(socketId)
      skip if socket.userId === message.senderId (sender gets raw)
      typeKey = socket.typeKey || 'unknown'  ← fallback for missing profile
      groups[typeKey].socketIds.push(socketId)

    Maximum groups: 9 (3 response values × 3 medium values)
    Regardless of room size, at most 9 Groq calls needed.

    Edge case: if typeKeys.length === 0 (only sender in room):
      → still calls _deliverToSender(io, message) and returns

  STEP 3: Batch-check Redis cache — ONE pipeline round trip
    const contentHash = hashContent(message.rawContent)  [from reframeCache.js]
    for each typeKey: cachePipelineRead.get(`reframe:${contentHash}:${tk}`)
    cacheResults = await cachePipelineRead.exec()

  STEP 4: Separate hits from misses
    hits = { typeKey: cachedString }
    misses = [ typeKey, ... ]  (need Groq call)

  STEP 5: Call Groq for misses — ALL IN PARALLEL (Promise.all)
    groqResults = await Promise.all(misses.map(async (tk) => {
      const reframed = await reframeMessage(rawContent, tk)
      return { tk, reframed }
    }))

    Why parallel not sequential:
      Sequential: 5 misses × 150ms = 750ms total latency
      Parallel:   max(all call latencies) ≈ 150ms regardless of miss count

  STEP 6: Write new reframes to Redis — ONE pipeline round trip
    for each groqResult: cachePipelineWrite.set(`reframe:${hash}:${tk}`, reframed, 'EX', 3600)
    Also merges into hits map: hits[tk] = reframed
    Only runs if groqResults.length > 0

  STEP 7: Deliver to each socket
    for each (typeKey, group) in Object.entries(groups):
      content = hits[typeKey] ?? message.rawContent  [fallback to raw]
      for socketId in group.socketIds:
        io.to(socketId).emit('new_message', {
          ...message,
          content,                      // ← reframed for this typeKey
          rawContent: message.rawContent // ← preserved for display/toggle
        })

  STEP 8: Deliver raw to sender via _deliverToSender(io, message)

Internal _deliverToSender(io, message):
  Gets roomSockets from adapter (NOT all server sockets — important bug fix)
  Iterates room's socket set looking for socket.userId === message.senderId
  Emits 'new_message' with content set to rawContent (sender sees original)
  BUG FIX note: Previously iterated io.sockets.sockets (ALL connected sockets
  on the server across ALL rooms). Now iterates only the room's socket set —
  correct and O(room size) instead of O(total connected users).

Scaling math example:
  Room of 50 users, 5 unique personality types, cold cache:
    Before fix: 49 Groq calls (one per recipient)
    After fix:  5 Groq calls (one per unique typeKey, all parallel)
    Warm cache: 0 Groq calls
    Redis round trips: 2 (1 read pipeline + 1 write pipeline)

--- 9.11 GROQ SERVICE: src/services/groq.js ---

Purpose: Wraps Groq SDK for personality-aware message reframing.

Model: llama-3.1-8b-instant
  const MODEL = 'llama-3.1-8b-instant'
  Note: llama3-8b-8192 was decommissioned. Same capability, new model ID.
  Fast inference (~150ms on Groq's infrastructure)
  8192 context window (more than enough for a single chat message)

Initialization:
  Groq SDK reads GROQ_API_KEY from process.env automatically.
  If key missing: logs a console.warn (not an error — graceful degradation)
  new Groq({ apiKey: process.env.GROQ_API_KEY })

reframeMessage(rawContent, recipientTypeKey) → Promise<string>:
  - Fast-path: return rawContent immediately if !process.env.GROQ_API_KEY
  - System prompt:
      "You are a subtle communication translator. Reframe how a chat message
       SOUNDS to a specific personality type — same facts, different tone.
       Under 2 sentences. Never reveal you're reframing."
  - User prompt:
      `Message: '${rawContent}'\nRecipient type: ${typeKey}\nReframe for this personality.`
  - temperature: 0.7 (creative but not random)
  - max_tokens: 150 (keep it short — reframing not expanding)
  - On any error (429, 401, timeout, network): return rawContent unchanged
    [Graceful degradation — app works as normal chat if Groq is down]
  - If model returns empty: return rawContent

Why NOT streaming:
  Streaming delivers the first token faster, but we deliver to multiple sockets
  simultaneously. Getting the full string first lets us emit once to a group.
  Managing per-group streams adds complexity for minimal UX gain in a chat context.

--- 9.12 SENTIMENT SERVICE: src/services/sentiment.js ---

Purpose: Analyzes message sentiment and updates room emotional weather.
         BOTTLENECK FIX #6: called via setImmediate — never blocks message delivery.

Constants:
  WEATHER_WINDOW = 20  (rolling window size)
  WEATHER_TTL    = 120 (seconds — hash expires if room goes quiet)

analyzeMessage(text) → { score }:
  - Uses 'sentiment' npm package (AFINN-165 word list, synchronous, ~1ms, no API)
  - Returns result.comparative (score normalized by word count)
  - Clamped to [-5, 5] via Math.max(-5, Math.min(5, result.comparative))
  - On error: returns { score: 0 } (neutral fallback, never crashes)
  - Examples: "This is great!" → ~3, "I'm frustrated" → ~-3, "Meeting at 3pm" → 0

updateRoomWeather(roomId, score, timestamp):
  STEP 1: Append to rolling window (one write pipeline — ONE round trip)
    writePipeline.lpush("weather:{roomId}", String(score))
    writePipeline.ltrim("weather:{roomId}", 0, WEATHER_WINDOW - 1)  // 0-19 = 20 items
    writePipeline.lpush("weatherts:{roomId}", String(timestamp))
    writePipeline.ltrim("weatherts:{roomId}", 0, WEATHER_WINDOW - 1)
    await writePipeline.exec()

  STEP 2: Read rolling window (separate read pipeline — ONE round trip)
    readPipeline.lrange("weather:{roomId}", 0, WEATHER_WINDOW - 1)
    readPipeline.lrange("weatherts:{roomId}", 0, WEATHER_WINDOW - 1)
    const [[, rawScores], [, rawTimestamps]] = await readPipeline.exec()

  STEP 3: Compute metrics
    scores     = rawScores.map(parseFloat)
    timestamps = rawTimestamps.map(ts => parseInt(ts, 10))
    avgScore:   mean of scores array
    velocity:   count of timestamps where (now - ts < 60_000) [messages per minute]
    volatility: standard deviation of scores (emotional swings)
      mean     = avgScore
      variance = scores.reduce((sum, s) => sum + (s - mean) ** 2, 0) / scores.length
      volatility = Math.sqrt(variance)

  STEP 4: Determine weather state (priority order — most extreme checked first)
    'stormy'  — avgScore > 4 OR velocity > 15  (overwhelming or very fast)
    'warm'    — avgScore > 2 AND volatility < 1  (consistently good vibes)
    'heated'  — avgScore > 2  (positive but volatile)
    'stormy'  — avgScore < -2 AND volatility > 2  (negative + chaotic)
    'tense'   — avgScore < -2  (negative but steady)
    'calm'    — default (neutral)

  STEP 5: Persist to Redis HASH
    HSET "roomweather:{roomId}" { state, avgScore: toFixed(2), velocity: int, volatility: toFixed(2) }
    EXPIRE "roomweather:{roomId}" 120

  STEP 6: Publish to Redis channel "weather:{roomId}"
    const weatherPayload = JSON.stringify({ state, avgScore, velocity, volatility })
    redis.publish("weather:{roomId}", weatherPayload)
    pubsub.js receives and forwards to io.to(roomId).emit('weather_update', ...)

--- 9.13 REFRAME CACHE: src/services/reframeCache.js ---

Purpose: Redis cache layer for Groq reframe results. Exports hashContent().

hashContent(text) → 16-char hex string:
  Uses Node.js built-in crypto module (no external dependency)
  createHash('sha256').update(text).digest('hex').slice(0, 16)
  Why sha256: stable, collision-resistant, compact (500-char message → 16 chars)
  Why slice(0,16): 64-bit is more than collision-resistant for a chat app

Cache key format: "reframe:{hashContent(rawContent)}:{typeKey}"
  Example: "reframe:a3f1b2c4d5e6f7a8:analytical:verbal"
  buildKey() is an internal helper (not exported)

Exported functions:
  getCached(rawContent, typeKey) → string | null
    redis.get(buildKey(rawContent, typeKey))
    Returns null on miss or Redis error (treats as miss)

  setCached(rawContent, typeKey, reframed) → void
    redis.set(buildKey(...), reframed, 'EX', 3600)
    Returns silently on Redis error — caching failure never breaks delivery

TTL: 3600s (1 hour). Chat messages are ephemeral.

IMPORTANT NOTE: In reframeHandler.js, getCached/setCached are NOT used as
individual calls. reframeHandler.js directly builds cache keys and uses pipeline
operations for batch reads/writes. Only hashContent() is imported from this file.
getCached/setCached are still useful utilities for single-item operations.

--- 9.14 BACKGROUND JOB: src/jobs/syncRoomCounts.js ---

Purpose: Write-behind caching sync — Redis INCR counters → Postgres every 60s.
         BOTTLENECK FIX #5.

The problem with naive Postgres approach:
  UPDATE rooms SET synced_count = synced_count + 1 WHERE id = $roomId
  Two concurrent messages: both try to read-increment-write the same row.
  One transaction must wait for the other's row lock. At high throughput:
  lock queue forms → serial writes → severe degradation.

The fix: Redis INCR "msgcount:{roomId}" per message.
  Redis is single-threaded → INCR is always atomic, no locks, sub-millisecond.
  This job reads the accumulated counts and syncs to Postgres once per minute.

startSyncJob():
  Logs start message
  Calls syncRoomCounts() immediately (no waiting for first interval)
  Returns setInterval(syncRoomCounts, 60_000) — cleared on graceful shutdown

syncRoomCounts():
  1. redis.keys('roomcount:*')  [acceptable KEYS here: runs 1/min, rooms bounded]
  2. Pipeline: GET for all keys → ONE round trip
  3. Build updates array: { roomId, count } for each key (filter count > 0)
  4. Promise.all: supabaseAdmin.from('rooms').update({ synced_count: count }).eq('id', roomId)
  5. Logs count of rooms synced
  6. On error: logs but does NOT crash (sync failure doesn't affect chat)

Note: KEYS is O(N) on all Redis keys and generally an anti-pattern (Bottleneck #3).
However, this job runs only once per minute on a background timer, not on the hot
request path. The number of rooms is bounded and small. For very large deployments:
replace with SCAN to avoid momentarily blocking Redis.

--- 10.6 useSocket HOOK: hooks/useSocket.js ---

Manages Socket.io connection lifecycle.

useSocket(roomId) → { socket, connected }

Connection:
  1. supabase.auth.getSession() → get access_token (returns early if no session)
  2. io(API_URL, {
       auth:       { token: session.access_token },
       transports: ['websocket'],  // WebSocket only — skip long-polling
       reconnection: true,
       reconnectionAttempts: 10,
       reconnectionDelay:    1000,
     })
  3. socketRef.current = socket (stored in ref, not state)
  4. socket.on('connect')      → setConnected(true) + console.log
  5. socket.on('disconnect')   → setConnected(false) + console.log
  6. socket.on('connect_error') → setConnected(false) + console.error

Heartbeat:
  setInterval every 20,000ms (HEARTBEAT_INTERVAL_MS):
    if socket.connected && roomId: socket.emit('heartbeat', { roomId })
  [Keeps "presence:{roomId}:{userId}" TTL alive — server TTL is 30s]

  NOTE: The second useEffect on roomId is empty (no body) — roomId updates
  are naturally picked up by the heartbeat closure on next tick.

Cleanup on unmount:
  clearInterval(heartbeatRef.current)
  socket.disconnect()
  socketRef.current = null

Returns { socket: socketRef.current, connected }
  Note: returns ref value (not state) to avoid re-renders on socket events.
  connected is state (triggers re-renders for UI updates).

API_URL: import.meta.env.VITE_API_URL || 'http://localhost:3001'

--- 10.7 useRoom HOOK: hooks/useRoom.js ---

Room state management — wraps useSocket with all room-level logic.

useRoom(roomId) → { socket, messages, setMessages, onlineUsers, isLoading,
                    connected, toast, sendMessage }

Constants:
  CLIENT_RATE_LIMIT     = 30
  CLIENT_RATE_WINDOW_MS = 60_000

Client-side rate limiting:
  msgCountRef = useRef(0)
  rateLimitTimer = useRef(null)
  On first message: setTimeout(reset, CLIENT_RATE_WINDOW_MS)
  If count > limit: showToast('Slow down — max 30 messages per minute')
  [UX-only guard: instant feedback without server round trip]
  [Server Redis token bucket is the real enforcer]

Socket event handlers (registered when socket + roomId change):
  On mount: socket.emit('join_room', { roomId }) + setIsLoading(true)

  'room_history': setMessages(history || []) + setIsLoading(false)

  'new_message': deduplication by id
    setMessages(prev => prev.some(m => m.id === msg.id) ? prev : [...prev, msg])

  'online_users': setOnlineUsers(users || [])

  'user_joined': add to onlineUsers (dedup by userId)

  'user_left': filter from onlineUsers by userId

  'rate_limited': showToast(message || fallback)

On unmount:
  socket.emit('leave_room', { roomId })
  socket.off for all above events
  Reset messages, onlineUsers, isLoading to defaults

Reconnect toasts (SEPARATE effect — protects socket.io internal handlers):
  socket.on('connect', onConnect)  → showToast('Back online ✓', 'success')
                                   → re-emit 'join_room' to recover missed messages
  socket.on('disconnect', onDisconnect) → showToast('Reconnecting…', 'warn')
  Cleanup: socket.off('connect', onConnect) — removes ONLY our listener (not all)
  [Separate effect with named functions so cleanup never removes socket.io's own handlers]

sendMessage(content):
  1. Validate: socket connected, roomId exists, content.trim().length <= 500
  2. Client-side rate check (msgCountRef)
  3. socket.emit('send_message', { roomId, content: trimmed })

setMessages is exposed in return value for optimistic UI (MessageInput could use it)

--- 10.8 useWeather HOOK: hooks/useWeather.js ---

Listens to 'weather_update' socket events.

--- 10.9 useUnread HOOK: hooks/useUnread.js ---

Tracks unread message counts per room WITHOUT triggering re-renders.

Why useRef:
  Unread counts update on EVERY incoming message (even background rooms).
  useState would re-render the entire sidebar on every message.
  useRef stores counts silently — sidebar badges re-render only on room switch.

countsRef.current = { [roomId]: count }

updateTitle() — called manually after modifying counts:
  total = sum of all counts
  If total > 0 && document.hidden: document.title = `(${total}) EchoChamber`
  Else: document.title = 'EchoChamber'

Effects:
  1. On visibilitychange → visible: clear(activeRoomId) + updateTitle()
  2. On activeRoomId change: countsRef.current[activeRoomId] = 0 + updateTitle()

Public API:
  increment(roomId): skip if (roomId === activeRoomId && !document.hidden)
                     else: count += 1, updateTitle()
  clear(roomId): count = 0, updateTitle()
  getCount(roomId): return count || 0

--- 10.12 MessageList COMPONENT: components/MessageList.jsx ---

Virtualized message list — renders only ~30 visible messages.
BOTTLENECK FIX #9: Virtual scrolling.

Props: { messages, isLoading, currentUserId, currentUserProfile }

Virtualization constants:
  ITEM_HEIGHT  = 72  (estimated average message height in px)
  BUFFER_ABOVE = 10  (extra items above visible window)
  BUFFER_BELOW = 20  (extra items below visible window)

Scroll tracking:
  handleScroll(): reads scrollTop from containerRef.current

  [Auto-scroll only triggers if user was already at bottom]

  Default 600px before measurement

  visibleCount = Math.ceil(containerH / ITEM_HEIGHT)
  startIndex = Math.max(0, Math.floor(scrollTop / ITEM_HEIGHT) - BUFFER_ABOVE)
  endIndex = Math.min(messages.length, startIndex + visibleCount + BUFFER_ABOVE + BUFFER_BELOW)
  visibleMessages = messages.slice(startIndex, endIndex)
  spacerTop = startIndex × ITEM_HEIGHT     [div above visible items]
  spacerBottom = Math.max(0, (messages.length - endIndex) × ITEM_HEIGHT)

Spacer divs maintain correct scroll height so scrollbar behaves naturally.

11. DATA FLOW — MESSAGE LIFECYCLE
================================================================================

When User A sends "Hey everyone!" in a room with 3 other users:

[CLIENT A]
  MessageInput → handleSend()
  1. Client-side rate limit check (msgCountRef in useRoom + canSendRate in MessageInput)
  2. socket.emit('send_message', { roomId, content: "Hey everyone!" })

[BACKEND — send_message handler]
  3.  Redis INCR "ratelimit:{userA}"  [rate check]
  4.  Build message object: { id: uuid(), roomId, senderId, rawContent: "Hey everyone!",
      content: "Hey everyone!", sentAt, senderProfile: socket.profile, instanceId }
      (no Redis calls — senderProfile from socket object)
  5.  PIPELINE (1 round trip):
        LPUSH "history:{roomId}" messageJson
        LTRIM "history:{roomId}" 0 49
        INCR "msgcount:{roomId}"
        PUBLISH "room:{roomId}" messageJson

  6.  Supabase insert — fire and forget (no await)
      userClient.from('messages').insert({id, room_id, sender_id, content, sent_at}).then(...)

  7.  reframeAndDeliver(io, message) — AWAIT:
        a. Get all sockets in room (io.sockets.adapter.rooms)
        b. Group by typeKey (no Redis calls — profiles on socket objects)
           e.g. group A: "analytical:verbal" [User B]
                group B: "emotional:visual"   [User C]
                group C: "avoidant:auditory"  [User D]
        c. Pipeline: GET reframe cache for all 3 typeKeys (1 round trip)
        d. Cache misses → Promise.all([Groq("analytical:verbal"), Groq("emotional:visual"),
                                        Groq("avoidant:auditory")]) — all parallel ~150ms
        e. Pipeline: SET new cache entries with EX 3600 (1 round trip)
        f. Emit to each socket:
           User B receives: "Hey everyone!" (analytical:verbal tone)
           User C receives: "Hey everyone!" (emotional:visual tone)
           User D receives: "Hey everyone!" (avoidant:auditory tone)
           User A (sender) receives: "Hey everyone!" (raw, unmodified)

  8.  setImmediate(() => {
        const { score } = analyzeMessage("Hey everyone!")  → score ≈ 2
        updateRoomWeather(roomId, score, Date.now())
      })  ← runs AFTER step 7 completes (next event loop tick)

[BACKEND — weather update (next event loop tick)]
  9.  PIPELINE: LPUSH/LTRIM weather + weatherts lists (1 round trip)
  10. PIPELINE: LRANGE both lists (1 round trip)
  11. Compute avgScore, velocity, volatility → determine state (e.g. 'warm')
  12. HSET "roomweather:{roomId}" { state, avgScore, velocity, volatility }
  13. EXPIRE "roomweather:{roomId}" 120
  14. redis.publish("weather:{roomId}", JSON.stringify({state, avgScore, velocity, volatility}))

[BACKEND — pubsub.js (pattern weather:*)]
  15. Receives weather publish → io.to(roomId).emit('weather_update', weather)

[CLIENT B, C, D]
  16. Receive 'new_message' with their personality-tailored version
  17. MessageList updates via setMessages (dedup check by id)
  18. MessageBubble renders with "reframed" badge (content !== rawContent)
  19. ~5-10ms later: receive 'weather_update' → RoomWeather canvas lerps to new state

Total path for message delivery: ~20ms (pipeline) + ~150ms (Groq parallel)
Weather arrives: ~5-10ms after delivery (separate event)

14. PERSONALITY SYSTEM EXPLAINED
================================================================================

The 5-question quiz maps to 5 personality dimensions:

  Question 1: WHERE would you rather be?
    1 = deep in the mountains → setting: 'nature'
    2 = at the ocean edge     → setting: 'ocean'
    3 = somewhere in the city → setting: 'urban'

  Question 2: WHEN do you feel most like yourself?
    1 = 3am  → time: 'night'
    2 = noon → time: 'day'
    3 = 6pm  → time: 'evening'

  Question 3: HOW do you respond to someone upset?
    1 = figure out what went wrong → response: 'analytical'
    2 = feel it with them          → response: 'emotional'
    3 = give them space            → response: 'avoidant'

  Question 4: WHERE do you feel most alive?
    1 = alone, in my own world      → social: 'introvert'
    2 = a small circle I trust      → social: 'ambivert'
    3 = a crowd, the bigger the better → social: 'extrovert'

  Question 5: HOW do you think best?
    1 = words and conversations → medium: 'verbal'
    2 = images and visuals      → medium: 'visual'
    3 = music and sound         → medium: 'auditory'

typeKey = `${response}:${medium}` — the reframe grouping key
  Possible values: analytical:verbal, analytical:visual, analytical:auditory,
                   emotional:verbal, emotional:visual, emotional:auditory,
                   avoidant:verbal, avoidant:visual, avoidant:auditory
  Maximum: 9 unique personality type combinations

color = COLOR_PALETTE[(sum of all 5 answers) % 12]
  Sum ranges from 5 (all 1s) to 15 (all 3s) → 11 distinct sums → 11 possible colors.
  (12th color only accessible if sum wraps, which it can't in 1-3 range with 5 questions)
  Same answers always produce same color (deterministic).

avatar = AVATAR_SHAPES[(answers[2] - 1) % 5]
  Q3 answer (1-3) → index 0-4 of shape array
  Shapes: circle (index 0), triangle (1), square (2), hexagon (3), star (4)
  Note: only 3 shapes accessible (answers 1,2,3 → indices 0,1,2)
  Hexagon and star would require answers > 3 (currently not possible)

15. EMOTIONAL WEATHER SYSTEM EXPLAINED
================================================================================

The room "emotional weather" is a live ambient background that reflects the
collective sentiment of the conversation in real-time.

How it works (end-to-end):
  1. Every message triggers analyzeMessage(rawContent) → score (-5 to +5)
     Uses AFINN-165 word list: "love" = +3, "hate" = -3, neutral words = 0
     Synchronous, ~1ms, no network call.

  2. setImmediate defers updateRoomWeather — called AFTER message delivery.

  3. Redis stores rolling window of last 20 scores + timestamps:
     LPUSH/LTRIM "weather:{roomId}" and "weatherts:{roomId}"

  4. Three metrics computed from the rolling window:
     avgScore:   mean sentiment (positive = happy, negative = tense)
     velocity:   messages in last 60 seconds (high = fast-paced conversation)
     volatility: standard deviation of scores (high = erratic/unstable mood)

  5. Weather state decision tree (priority order):
     avgScore > 4 OR velocity > 15   → 'stormy'  (extreme or very fast)
     avgScore > 2 AND volatility < 1 → 'warm'    (consistently positive)
     avgScore > 2                    → 'heated'  (positive but volatile)
     avgScore < -2 AND volatility > 2 → 'stormy' (negative + chaotic)
     avgScore < -2                   → 'tense'   (negative but steady)
     else                            → 'calm'    (neutral, default)

  6. State published to Redis "weather:{roomId}" channel → all instances forward
     to io.to(roomId).emit('weather_update', ...)

  7. Frontend RoomWeather.jsx receives 'weather_update' via useWeather hook.
     Canvas lerps smoothly to new state over ~3 seconds.

Canvas animation states:
  calm:   2 orbs, slow breathing (speed 0.008), cool blues/teals, ~11% opacity
  warm:   2 orbs, medium breathing (speed 0.010), golden yellows, ~18% opacity
  heated: 3 orbs, faster breathing (speed 0.015), amber/coral, ~17% opacity
  tense:  2 orbs, very slow (speed 0.005), deep indigo, ~8% opacity
  stormy: 4 orbs, fast speed (speed 0.025), red/crimson, ~16% opacity

Performance optimizations:
  - Page Visibility API: RAF skips drawing when tab is hidden (loop still schedules)
  - prefers-reduced-motion: static tint, no animation
  - Lerp transition prevents jarring state jumps (3 second smooth blend)
  - Weather TTL 120s: hash expires if room goes quiet (no stale state)

Weather on join:
  When a user joins a room, they immediately receive the current weather state
  via 'weather_update' emit in join_room handler (HGETALL "roomweather:{roomId}")
  so they don't have to wait for the next message.

16. GROQ REFRAMING SYSTEM EXPLAINED
================================================================================

Core idea: The SAME message is expressed differently for different personality types.
           An analytical person prefers direct, logical language.
           An emotional person prefers empathetic, feeling-based language.
           The same information, different tone.

The three-level optimization:

  LEVEL 1 — Type grouping (O(room) → O(personality types)):
    Instead of one Groq call per recipient (50 users = 49 calls),
    group recipients by typeKey (at most 9 unique groups).
    A 50-person room with 5 unique types = 5 calls, not 49.
    A 50-person room with 1 unique type = 1 call, not 49.

  LEVEL 2 — Redis caching (O(types) → O(cache misses)):
    Cache key: "reframe:{sha256(content).slice(0,16)}:{typeKey}"
    If the same message pattern has been seen before for a given personality
    type, return the cached reframe. Zero Groq calls.
    1-hour TTL: ephemeral content, no need to cache indefinitely.

  LEVEL 3 — Parallel execution (serial latency → single-call latency):
    Cache misses called with Promise.all — all parallel.
    5 misses × 150ms sequential = 750ms total.
    5 misses × 150ms parallel   = ~150ms regardless of count.

Groq prompt design:
  System: "You are a subtle communication translator. Reframe how a chat message
           SOUNDS to a specific personality type — same facts, different tone.
           Under 2 sentences. Never reveal you're reframing."
  User:   "Message: '{rawContent}'\nRecipient type: {typeKey}\nReframe for this personality."

  Why "Under 2 sentences": Prevents model from expanding terse messages to paragraphs.
  Why "Never reveal": Keeps the reframing invisible to the user (magic of the app).
  temperature: 0.7 — creative enough to shift tone, not so random it changes meaning
  max_tokens: 150 — short reframes, not essays

Graceful degradation:
  If Groq API is down, returns rawContent unchanged. App degrades to normal chat.
  No errors shown to users — they just see the original message.
  Missing GROQ_API_KEY: fast-path in reframeMessage() returns rawContent immediately.

The sender's experience:
  The sender ALWAYS sees their own raw message, unmodified.
  Reframing your own words would be confusing and break "sent successfully" feedback.

Users can toggle: click "[ see original ]" on a reframed bubble to see rawContent.
  The backend never stores reframed content — only raw is in Supabase.
  Reframing is always computed on-the-fly, always private to each user.

'unknown' typeKey fallback:
  If a socket somehow lacks a typeKey (profile missing), it's grouped under 'unknown'
  and receives rawContent (the ?? fallback in reframeHandler delivery step).

================================================================================
17. RATE LIMITING — TWO-LAYER SYSTEM
================================================================================

Layer 1 — Client-side (UX guard):
  Location: useRoom.js (msgCountRef) + MessageInput.jsx (canSendRate)
  Limit: 30 messages per 60 seconds
  Implementation: useRef counter + setTimeout reset (in MessageInput: setInterval countdown)
  Purpose: Instant user feedback without server round trip
  Security: NONE — can be bypassed. Client code is client code.
  UX: Shows countdown timer "⏳ Rate limited — wait Xs"

Layer 2 — Server-side (authoritative enforcer):
  Location: roomHandler.js send_message handler
  Implementation: Redis token bucket
    INCR "ratelimit:{userId}"
    On first message (count === 1): EXPIRE "ratelimit:{userId}" 60
    If count > 30: emit 'rate_limited' → return
  Note: INCR+EXPIRE is not perfectly atomic (crash between them = key without TTL)
        Production solution: Lua script atomically does both in one command.

Why two layers?
  Client gives instant feedback (no latency).
  Server actually enforces the limit (security, fairness).
  "Never trust the client for security-critical limits."

================================================================================
18. HORIZONTAL SCALING DESIGN
================================================================================

The app supports multiple server instances (e.g., multiple Render instances)
through Redis Pub/Sub as the cross-instance message bus.

Single instance:
  User A sends → roomHandler publishes to "room:{roomId}" → pubsub.js receives →
  instanceId matches → SKIP (reframeAndDeliver already handled it) → done

Multi-instance (e.g., User A on Server 1, User B on Server 2):
  User A sends → Server 1 roomHandler publishes to "room:{roomId}"
  Server 1 pubsub.js: instanceId matches → SKIP (reframeAndDeliver handles Server 1 clients)
  Server 2 pubsub.js: instanceId DIFFERS → reframeAndDeliver(io, message)
  Server 2 delivers reframed version to User B (connected to Server 2)

All instances share:
  - Redis (Upstash) — same URL → same Pub/Sub channels, same keys
  - Supabase — same DB URL → same profiles, rooms, messages

The instanceId stamps every message in the pipeline.publish() call so pubsub.js
can differentiate its own instance's messages from other instances' messages.

Redis keys that work across instances (global state):
  - auth:{token} cache (any instance can validate any user's token)
  - profile:{userId} hash (any instance reads the same profile)
  - history:{roomId} list (any instance reads the same message history)
  - room:{roomId}:members set (presence is global across instances)
  - weather:{roomId} lists + roomweather hash (global weather state)

22. INTERVIEW CHEAT SHEET
================================================================================

Question: What does this app do?
Answer: "Same message, different experience per recipient. Groq reframes the
        tone by personality type — at most 9 LLM calls per message regardless
        of room size, because users are grouped by typeKey."

Question: How did you handle the LLM scaling problem?
Answer: "Grouped recipients by personality type — 9 combinations max — and cached
        reframes in Redis. A 50-person room goes from 49 calls to 5 or fewer.
        Cache misses are fired in parallel with Promise.all, so total latency is
        one call's duration (~150ms) regardless of how many groups miss the cache."

Question: Why Redis Pub/Sub?
Answer: "Cross-instance message delivery. User A on Server 1 sends a message —
        Redis Pub/Sub fans it out to Server 2 where User B is connected. Each
        instance subscribes to 'room:*' and delivers to its own connected sockets."

Question: What data structure for presence? Why?
Answer: "Redis Set per room. SADD on join, SREM on leave, SMEMBERS for the full
        list. Never KEYS — that scans the entire database O(total keys). SMEMBERS
        is O(room members) which is exactly the set you need."

Question: How do you avoid blocking message delivery?
Answer: "setImmediate defers weather computation to after the emit. The message
        reaches clients first — reframeAndDeliver completes — then on the very
        next event loop tick, sentiment analysis begins. Users never wait for
        weather updates."

Question: How do you scale Redis commands under the free tier?
Answer: "Pipeline. Four individual commands at 20ms each would add 80ms to every
        message send. A pipeline collapses that to ~20ms regardless of how many
        commands are in the batch. Reduces both latency and command count."

Question: What happens if Groq is down?
Answer: "Graceful fallback — raw message delivered unchanged. App degrades to
        normal chat, nothing breaks. The reframeMessage function catches all
        errors and returns rawContent. If GROQ_API_KEY is missing entirely,
        it fast-paths and returns rawContent immediately — no API call attempted."

Question: How would you scale beyond the free tier?
Answer: "Redis cluster for throughput, Groq paid tier or self-hosted Ollama for
        the LLM, Supabase Pro for database, multiple Render instances all
        connected via the same Redis Pub/Sub. The instanceId pattern already
        handles multi-instance without code changes."

Question: Why token caching in Redis for auth?
Answer: "supabase.getUser(token) is a network call (~50-100ms). 50 concurrent users
        all making requests = 50 parallel round trips to Supabase's auth server.
        Caching token→userId in Redis for 5 minutes means at most 1 Supabase
        call per 5-minute window per token. The trade-off: forced logouts have a
        5-minute staleness window — acceptable for chat, not for banking."

Question: Why write-behind caching for room counts?
Answer: "UPDATE rooms SET count+1 under concurrent inserts causes row-level lock
        contention — two messages arriving simultaneously both try to
        read-increment-write the same row, creating a lock queue. Redis INCR is
        atomic (single-threaded event loop) — no locks, sub-millisecond. A
        background job syncs to Postgres every 60 seconds."

Question: What's the instanceId for?
Answer: "roomHandler publishes to Redis AND calls reframeAndDeliver. The Pub/Sub
        subscriber runs in the SAME process and receives the publish immediately.
        Without instanceId, the subscriber would emit the raw message BEFORE
        reframeAndDeliver finishes — the frontend deduplicates by ID, so the raw
        version would always win. With instanceId, same-instance messages are
        skipped by the subscriber. Cross-instance messages (horizontal scaling)
        are routed through reframeAndDeliver on the receiving instance."

Question: Why React.memo with custom comparator on MessageBubble?
Answer: "Every new message triggers a re-render of the parent list, which without
        memo triggers re-renders of all visible MessageBubble components. With a
        custom comparator checking message id, content, and status, a bubble only
        re-renders if its own content changed (which happens during streaming or
        status updates). 100 messages visible = 99 prevented re-renders per message."

Question: What is the 'unknown' typeKey fallback?
Answer: "In reframeAndDeliver, if a socket somehow lacks a typeKey (e.g. profile
        was missing at connection time), it's grouped under 'unknown'. The delivery
        step uses `hits[typeKey] ?? message.rawContent` — so 'unknown' falls back
        to raw content. Users still receive the message, just unframed."

Question: Why does setMessages in useRoom expose setMessages in the return value?
Answer: "It's exposed for potential optimistic UI — the MessageInput could
        immediately push a 'sending...' state message before the server
        confirms. The server response then overwrites or deduplicates it by id."

Question: How does the Groq model key work in the code?
Answer: "groq.js uses const MODEL = 'llama-3.1-8b-instant'. A comment notes that
        llama3-8b-8192 was decommissioned — same capability, updated model ID.
        The Groq SDK reads GROQ_API_KEY from process.env automatically."
